Asynchronous Communication — Fixing Kafka For Real

The notice-board piece from the big picture was already wired into Order and Payment's code since Lesson 4 — it just never had a working broker underneath it. That changes now, and the whole chain from Lesson 7 should finally succeed.

What was actually broken (an infra bug, not a code bug)

docker-compose.yml pinned confluentinc/cp-kafka:latest and cp-zookeeper:latest. Confluent's latest tag currently resolves to Kafka 4.x, which dropped Zookeeper support entirely in favor of KRaft mode — but the compose file's environment variables (KAFKA_ZOOKEEPER_CONNECT, etc.) are Zookeeper-only config. Result: the container crash-looped from the very first lesson that touched Kafka, with Error: environment variable "KAFKA_PROCESS_ROLES" is not set — because the image expected KRaft config that was never provided.

The fix Pinned both images to 7.6.1 (Confluent Platform 7.6.1 = Kafka 3.7, the last major line with full Zookeeper support) — matching the Zookeeper-style config the compose file already had. Real-world lesson, not specific to this repo: a floating :latest tag on infrastructure you depend on long-term is a liability — it can silently break on a plain docker compose pull/recreate, with no code change on your side at all. Pin versions for anything you're not actively tracking upstream releases of.

Declaring topics as code

Both Order and Payment declare their Kafka topic as a Spring bean, not just a string scattered in producer code:

@Configuration
public class KafkaOrderTopicConfig {
  @Bean
  public NewTopic orderTopic() {
    return TopicBuilder.name("order-topic").build();
  }
}

order/.../config/KafkaOrderTopicConfig.java · payment/.../configuration/KafkaPaymentTopicConfig.java

Spring's KafkaAdmin auto-creates any NewTopic bean against the broker once it's reachable — no manual kafka-topics --create needed. This is why payment-topic may already exist even before you send your first successful message: the topic-creation and the message-sending are two separate concerns.

Recap: the producers (from Lesson 4), now actually working

NotificationProducer (Payment) and OrderProducer (Order) haven't changed at all since Lesson 4 — same fire-and-forget kafkaTemplate.send(message) call. The only thing that changed is that a real broker now exists to receive it.

Hands-on: rerun Lesson 7's order, expect it to actually work

STEP 1

Confirm Kafka's healthy:

docker compose ps kafka zookeeper
docker exec ms_kafka kafka-topics --bootstrap-server localhost:9092 --list

Both containers Up, and you should see payment-topic listed already.

STEP 2

Restart order-service and payment-service (Ctrl+C, ./mvnw spring-boot:run again) so their Kafka producers reconnect cleanly against the now-working broker.

STEP 3

Fire the exact same order request from Lesson 7, Step 4 (fresh product/customer ids if you want a clean read):

curl -i -X POST http://localhost:8222/api/v1/orders \
  -H "Content-Type: application/json" \
  -d '{
    "reference": "order-ref-002",
    "amount": 199.98,
    "paymentMethod": "PAYPAL",
    "customerId": "<your customer id>",
    "products": [ { "productId": 2, "quantity": 1 } ]
  }'

✓ Expect 200 with a real order id this time — the whole chain (Customer lookup → Product purchase → Order+OrderLine save → Payment call → Kafka publish) completed without throwing.

STEP 4

Verify, the same way you did after Lesson 7's failure — but this time expect real rows, not an orphan:

docker exec ms_pg_sql psql -U alibou -d order -c 'SELECT * FROM customer_order;'
docker exec ms_pg_sql psql -U alibou -d payment -c 'SELECT * FROM payment;'

This time the payment.order_id should point at a row that actually exists in customer_order — the exact inconsistency from Lesson 7 is gone.

STEP 5

Read the real event off the topic directly — nobody's consuming it yet (that's next lesson), so it's just sitting in Kafka:

docker exec ms_kafka kafka-console-consumer \
  --bootstrap-server localhost:9092 \
  --topic order-topic \
  --from-beginning \
  --max-messages 1

✓ You should see the raw JSON OrderConfirmation payload — reference, amount, payment method, the customer, and the purchased products. This is the actual message a Notification service will pick up in Section 15.

Check your recall

Why did fixing this require no changes to any service's Java code?

The bug was entirely in infrastructure (the Docker image version), not application logic. NotificationProducer and OrderProducer were correct from Lesson 4 onward — they just had nothing listening on localhost:9092 to send to.

Now that Kafka works, is the max.block.ms: 3000 override from Lesson 4 still doing anything?

Effectively no — with a healthy broker, metadata resolves almost instantly, well under 3 seconds, so the lower ceiling never gets hit. It's harmless to leave in place (still a safety net if Kafka ever goes down again) rather than something that needs reverting.
