The Config Server

One place holds every microservice's settings, instead of each service carrying its own application.yml in isolation.

Why this exists

Picture 8 services, each with database credentials, ports, and feature flags baked into its own jar. Change a password and you now edit and redeploy 8 things. The config server flips this: it's one small Spring Boot app whose entire job is to serve config files over HTTP. Every other service asks it "what are my settings?" on startup instead of shipping the answer itself.

How this repo does it

The whole server is one annotation:

@EnableConfigServer
@SpringBootApplication
public class ConfigServerApplication { ... }

services/config-server/src/main/java/.../ConfigServerApplication.java

Its own application.yml tells it to run in native mode — read config files straight off the classpath, instead of the more common setup of pulling them from a Git repo:

server:
  port: 8888
spring:
  profiles:
    active: native
  cloud:
    config:
      server:
        native:
          search-locations: classpath:/configurations

services/config-server/src/main/resources/application.yml

Inside configurations/ there's one YAML file per service — customer-service.yml, order-service.yml, gateway-service.yml, etc. The filename is the lookup key. customer-service.yml holds the customer service's Mongo connection details:

server:
  port: 8090
spring:
  data:
    mongodb:
      username: alibou
      password: alibou
      host: localhost
      port: 27017
      database: customer

services/config-server/src/main/resources/configurations/customer-service.yml

And on the other end, the customer service itself just points at the config server and names itself — that name is what gets matched to the filename above:

spring:
  config:
    import: optional:configserver:http://localhost:8888
  application:
    name: customer-service

services/customer/src/main/resources/application.yml

The pattern to remember A client service's spring.application.name is the key. The config server matches it to a file named <that-name>.yml and hands back its contents over plain HTTP, as JSON.

Hands-on: run it and see the config get served

STEP 1

Infra containers (Postgres, MongoDB, Kafka, Zipkin, MailDev) should already be up via docker compose up -d in the repo root. Confirm with docker compose ps — all should say running.

STEP 2

Start the config server on its own:

cd services/config-server
./mvnw spring-boot:run

Wait for a line like Tomcat started on port 8888.

STEP 3

In another terminal, ask it for customer-service's config directly — this is exactly the request every microservice makes on startup:

curl http://localhost:8888/customer-service/default

You should get back JSON containing a propertySources entry with the Mongo host, port, and database values from the YAML above. ✓ That response is centralized config working — no service had to hardcode it.

STEP 4

Try one more: curl http://localhost:8888/order-service/default — different service name, different file, same server.

Check your recall

What does a client service send to the config server so it gets the right file back?

Its spring.application.name — the config server matches that string to a <name>.yml file in configurations/.

Why "native" mode here instead of the more typical Git-backed config server?

Simplicity for a local/teaching setup — files live on the classpath instead of requiring a separate Git repo to clone and poll. Same contract to clients either way; only the config server's own source of truth changes.

Primary source

Spring Cloud Config Server reference docs — read the "Environment Repository" section to see the Git-backed option this repo skipped, and why native mode exists as an alternative.
