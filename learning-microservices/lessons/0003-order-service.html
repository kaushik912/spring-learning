The Order Service

Same six-layer shape as Customer — but relational (Postgres/JPA) instead of document (Mongo), with a real one-to-many relationship, and a first look at a service that reaches out to other services.

Entity: a real relationship this time

Order owns a list of OrderLine (one order, many line items — one per product purchased). It also auto-tracks created/modified timestamps via Spring Data's auditing listener:

@Entity
@EntityListeners(AuditingEntityListener.class)
@Table(name = "customer_order")
public class Order {
  @Id @GeneratedValue
  private Integer id;
  private String reference;
  private BigDecimal totalAmount;
  @Enumerated(EnumType.STRING)
  private PaymentMethod paymentMethod;
  private String customerId;            // <- just an ID, not a joined Customer object
  @OneToMany(mappedBy = "order")
  private List<OrderLine> orderLines;
  @CreatedDate private LocalDateTime createdDate;
  @LastModifiedDate private LocalDateTime lastModifiedDate;
}

order/.../order/Order.java · orderline/OrderLine.java

Notice: customerId is a bare String, not a foreign key This is the microservices rule: Order's database has no idea Customer's database exists. They're different services with different databases (Postgres vs Mongo) — there's no SQL join possible across them even if you wanted one. Order just stores the customer's id and, when it needs real customer data, asks the customer service over HTTP. That's the next section.
Notice: ddl-auto: create Order's config sets spring.jpa.hibernate.ddl-auto: create — Hibernate drops and rebuilds the whole schema every time the service restarts. Great for a teaching repo where you want a clean slate each run; would lose all data in production (you'd use validate or a migration tool like Flyway there instead).

A preview: createOrder already reaches beyond this service

Open OrderService.java and createOrder does a lot: it calls a CustomerClient, a ProductClient, a PaymentClient, saves the order, saves order lines, calls the payment client again, then publishes a Kafka event. That's because this repo is the finished product — every later curriculum section's code is already sitting in the same file.

Why we can't run createOrder yet It needs, all at once: a running customer-service (have it ✓), a running product-service and payment-service (Section 8, not yet), a running Kafka (Section 13, not yet), and — look closely at Order's config — customer-url: http://localhost:8222/.... Port 8222 isn't customer-service's own port (8090) — it's the gateway's port (Section 11). So createOrder can't even reach Customer yet, because the gateway doesn't exist yet either.

We'll come back to this exact method once Payment, Product, and the Gateway are built — piece by piece, the same way the course does.

Check your recall (spot the bug)

Compare OrderMapper.toOrder against OrderRequest and Order:

public Order toOrder(OrderRequest request) {
  return Order.builder()
      .id(request.id())
      .reference(request.reference())
      .paymentMethod(request.paymentMethod())
      .customerId(request.customerId())
      .build();
}
One field from OrderRequest never makes it onto the saved Order. Which one, and what would you observe because of it?

request.amount() is never copied to order.totalAmount — the builder never calls .totalAmount(...). Every order saved this way will have totalAmount = null in the database, and GET /api/v1/orders/{id} will always report "amount": null back to the client, regardless of what amount was sent in on create. A real, un-caught bug in the reference repo — the kind of thing reading code carefully (rather than trusting it works because it compiles) catches.

Hands-on: boot it and prove the plumbing (not the full flow yet)

STEP 1

Confirm ms_pg_sql (Postgres) is up: docker compose ps. Config server should still be running from Lesson 1.

STEP 2 
cd services/order
./mvnw spring-boot:run

Watch the log for Hibernate's create table customer_order / create table customer_line — that's ddl-auto: create firing.

STEP 3

Confirm the tables exist via pgAdmin (http://localhost:5050) — or just prove the service is live:

curl http://localhost:8070/api/v1/orders

✓ Expect [] — an empty array, 200 OK. That's JPA + Postgres wired correctly end to end, with nothing in the table yet.

STEP 4

Check the 404 path:

curl -i http://localhost:8070/api/v1/orders/999

Expect 404 with the message from EntityNotFoundException, handled by GlobalExceptionHandler — same pattern as Customer's CustomerNotFoundException, different exception type (JPA's built-in one vs. a hand-rolled one).

Don't try POST yet POST /api/v1/orders will fail right now (it needs customer/product/payment/Kafka, all not running). We'll do this for real in a later lesson once those pieces exist.
