The Payment Service

The simplest service in the whole repo — one endpoint, no queries, no update, no delete. It exists to do exactly one thing: record that a payment happened, then tell the world about it.

Entity: same shape as Order, deliberately isolated

@Entity
@Table(name = "payment")
public class Payment {
  @Id @GeneratedValue
  private Integer id;
  private BigDecimal amount;
  @Enumerated(EnumType.STRING)
  private PaymentMethod paymentMethod;
  private Integer orderId;      // <- just an int, same rule as Order.customerId in Lesson 3
  @CreatedDate private LocalDateTime createdDate;
  @LastModifiedDate private LocalDateTime lastModifiedDate;
}

payment/.../payment/Payment.java

Postgres + JPA again, same as Order (see the big picture reference for why every service picks its own database independently). orderId is a bare integer — Payment's database has zero knowledge of Order's database, exactly like Order↔Customer in Lesson 3.

A new idea: each service defines its own local "Customer"

Look at PaymentRequest — it carries a nested Customer record:

public record PaymentRequest(
    Integer id, BigDecimal amount, PaymentMethod paymentMethod,
    Integer orderId, String orderReference,
    Customer customer
) {}

// payment/Customer.java — Payment service's OWN definition, not shared with customer-service
public record Customer(String id, String firstname, String lastname, String email) {}
This is not a bug or duplication mistake Payment service does not import a shared Customer class from customer-service. It defines its own minimal record with only the four fields it actually needs (to email a receipt later). This is a real microservices principle: no shared domain model library between services. Each service owns a narrow, local view of a concept it doesn't own. If customer-service adds 10 new fields to its real Customer tomorrow, Payment service is completely unaffected — it never sees them.

Service: save, then fire an async notification

public Integer createPayment(PaymentRequest request) {
  var payment = repository.save(mapper.toPayment(request));

  notificationProducer.sendNotification(
      new PaymentNotificationRequest(
          request.orderReference(), request.amount(), request.paymentMethod(),
          request.customer().firstname(), request.customer().lastname(), request.customer().email()
      )
  );
  return payment.getId();
}

payment/.../payment/PaymentService.java · notification/NotificationProducer.java

First taste of async (Kafka) — full detail comes in Section 13 notificationProducer.sendNotification(...) calls kafkaTemplate.send(message), which is fire-and-forget — it hands the message to Kafka's client library and returns immediately, without waiting for delivery confirmation. Compare this to Order's customerClient.findCustomerById(...) from Lesson 3, which blocks until it gets an HTTP response. Same goal (tell another part of the system something happened) — two completely different communication styles. This is the "notice board" from the big-picture table.

Controller: one endpoint, on purpose

@PostMapping
public ResponseEntity<Integer> createPayment(@RequestBody @Valid PaymentRequest request) {
  return ResponseEntity.ok(service.createPayment(request));
}

No GET, no list, no lookup-by-id. Payment records aren't meant to be browsed through this service's own API in this design — a real system would likely add read endpoints, but this teaching repo keeps Payment intentionally narrow: write-only, from the outside.

    }
  }'

✓ Expect a plain integer back — the new payment's id. Verify it landed in Postgres:

docker exec ms_pg_sql psql -U alibou -d payment -c 'SELECT * FROM payment;'
Verified: what actually happens with Kafka down This repo's docker-compose.yml Kafka image currently won't start (unrelated to the course: cp-kafka:latest now defaults to KRaft mode, the compose file still configures old-style Zookeeper mode — proper fix lands in Section 13). Two real, confirmed effects on createPayment:
  1. kafkaTemplate.send() isn't truly non-blocking on the first call — the producer has to fetch topic metadata first, and blocks up to max.block.ms (Kafka's default: 60s) trying to reach a broker that isn't there. We added max.block.ms: 3000 to payment-service.yml on the config server so it fails in 3s instead of hanging a minute.
  2. When it does fail, createPayment has no try/catch around the Kafka call — the exception bubbles up as an HTTP 500. But repository.save(...) already ran and committed before that failure — so the payment row is saved in Postgres even though the client got a 500. Verify it yourself: docker exec ms_pg_sql psql -U alibou -d payment -c 'SELECT * FROM payment;'
That second point is a genuine distributed-systems trap, not specific to this repo: a failed response doesn't always mean nothing happened. A caller that retries on 500 here would create a second payment row for the same order.

Check your recall

Why does Payment service define its own Customer record instead of reusing customer-service's?

No shared domain model across services — each service owns a narrow local view of only the fields it needs. Keeps services independently deployable: customer-service can change its real Customer class freely without breaking Payment.

If Kafka is completely down, does POST /api/v1/payments fail?

No — the HTTP response returns successfully (payment is saved to Postgres regardless) because kafkaTemplate.send() is async/fire-and-forget. The notification message is simply lost/retried in the background, not blocking the caller. Contrast with a failed synchronous call (like Order → Customer over HTTP), which does fail the whole request.
