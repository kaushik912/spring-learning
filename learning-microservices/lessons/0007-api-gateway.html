The API Gateway — and the First Full Order

The front-door piece from the big picture. This closes two loops at once: the mystery port 8222 from Lesson 3's config, and — for the first time — every piece is finally in place to attempt a real, full order.

The gateway is pure config — zero routing code

@SpringBootApplication
public class GatewayApplication {
  public static void main(String[] args) {
    SpringApplication.run(GatewayApplication.class, args);
  }
}

gateway/.../GatewayApplication.java

No annotation even hints at "gateway" — everything happens in config, because spring-cloud-starter-gateway reads route definitions from properties:

server:
  port: 8222
spring:
  cloud:
    gateway:
      routes:
        - id: customer-service
          uri: lb:http://CUSTOMER-SERVICE
          predicates:
            - Path=/api/v1/customers/**
        - id: order-service
          uri: lb:http://ORDER-SERVICE
          predicates:
            - Path=/api/v1/orders/**
        - id: product-service
          uri: lb:http://PRODUCT-SERVICE
          predicates:
            - Path=/api/v1/products/**
        - id: payment-service
          uri: lb:http://PAYMENT-SERVICE
          predicates:
            - Path=/api/v1/payments/**

config-server/.../configurations/gateway-service.yml

Port 8222 — remember this? Order's config (Lesson 3) had customer-url: http://localhost:8222/api/v1/customers. That wasn't a typo or a placeholder — it was always pointing at this service, which didn't exist yet. Order was written to talk to Customer/Product/Payment only through the gateway, never directly to their own ports (8090/8050/8060).

Reading a route: lb:http://CUSTOMER-SERVICE

Break this down:

  • Path=/api/v1/customers/** — the predicate: if an incoming request's path matches this, use this route
  • lb: — "load-balanced": don't treat the next part as a literal host, resolve it
  • http://CUSTOMER-SERVICE — resolve this name against Eureka (Lesson 6) to find a real host:port, then forward the request there

This only works because Eureka is running and Customer registered under exactly that name. Gateway, Eureka, and the config server are now all leaning on each other — this is the point in the course where the infrastructure pieces stop being independent demos and start being a real system.

Hands-on, part 1: prove the front door works

STEP 1

Everything from Lessons 1–6 should still be running: config-server, discovery, customer, order, payment, product. Start the gateway:

cd services/gateway
./mvnw spring-boot:run

Runs on port 8222.

STEP 2

Hit customer-service through the gateway instead of its own port 8090 — same path, different port:

✓ Same response you'd get from localhost:8090 directly — but this request actually traveled gateway → Eureka lookup → customer-service. Check the Eureka dashboard (localhost:8761) — GATEWAY should now be registered too (it's also a Eureka client).

Hands-on, part 2: the first real order

Every dependency createOrder needs is now technically reachable — except Kafka, which is still down (Section 13 hasn't happened yet). Let's try anyway and see exactly where it breaks — this tells us something real about how failures propagate across services.

    "amount": 199.98,
    "paymentMethod": "PAYPAL",
    "customerId": "<your customer id from Lesson 2>",
    "products": [ { "productId": 1, "quantity": 2 } ]
  }'

Report back what you get — a 200 with an order id, or an error. Given Kafka's state, a failure partway through is expected. Paste me the response (and the order-service console log around it) and we'll trace exactly which call in createOrder failed.

Predict before you look: what's left half-done? Think back to the dual-write problem you reasoned through after Lesson 4. createOrder calls Product (decrement stock), then saves Order+OrderLines locally, then calls Payment (which itself tries to notify over Kafka and may fail). If the Payment call throws, @Transactional rolls back Order's own database — but Product's stock decrement already committed in a different service's database, and it does not get undone. Check product 1's stock again after your attempt above — did it drop, even if the order itself failed?
Verified: the real failure, traced end to end A live run confirmed exactly this, plus one sharper detail. The error is feign.FeignException$InternalServerError at PaymentClient#requestOrderPayment — Payment's own createPayment 500'd (Kafka timeout, same as Lesson 4), Feign propagated that as an exception, and it was never caught inside createOrder. Checking all three databases after:
  • customer_order / customer_line — 0 rows. Rolled back by @Transactional, exactly as predicted.
  • product.available_quantity — dropped, permanently. Different service, different transaction — not rolled back.
  • payment — rows exist, and each one's order_id points at an Order id that was allocated in-memory by JPA before the transaction rolled back — a reference to an order that, from Order service's own tables, never existed.
Net effect: stock got reserved and a payment record got created for an order that doesn't exist anywhere in Order's database. No exception, log line, or reconciliation job catches this automatically — you'd only find it by noticing the mismatch, the way we just did with three manual psql queries.

Check your recall

Why does lb:http://CUSTOMER-SERVICE require Eureka specifically, not just any network address?

"CUSTOMER-SERVICE" isn't a hostname — it's the name a service registered under in Eureka. The lb: prefix tells Spring Cloud Gateway to resolve it via the registry (with load balancing across instances) rather than treating it as a literal address.

If a compensating step existed to "un-decrement" Product's stock when an order ultimately fails, what pattern would that be an example of?

A saga — a sequence of local transactions across services, each with a defined compensating action to undo it if a later step fails. This repo doesn't implement one (same simplification category as skipping the outbox pattern) — real systems handling money/inventory across services usually need this exact mechanism.
