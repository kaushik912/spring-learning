The Customer Service

The first real microservice: a self-contained REST API over its own MongoDB database, wired to the config server you ran in Lesson 1.

Why this exists

This is the template every other service in this repo copies. Six pieces, each with exactly one job. Once this shape is familiar, Order, Payment, and Product services will look like variations on the same theme, not new things to learn.

The six-layer shape

LayerClassJob
EntityCustomerWhat's actually stored in MongoDB
RepositoryCustomerRepositoryTalks to the database — no SQL/queries written by hand
Request DTOCustomerRequestWhat a client is allowed to send in
Response DTOCustomerResponseWhat a client is allowed to see out
MapperCustomerMapperConverts between Entity and DTOs
ServiceCustomerServiceThe actual business logic
ControllerCustomerControllerHTTP in, HTTP out
Why not just return the Entity directly? The DTO layer looks like duplication (same fields as Customer) but it's a deliberate seam: the database shape and the API shape are allowed to drift independently. Add an internal-only field to Customer tomorrow and it does not leak to clients unless you also add it to CustomerResponse.

Entity → Repository

Customer is a plain Mongo document — @Document maps the class to a collection, @Id marks the Mongo _id:

@Document
public class Customer {
  @Id
  private String id;
  private String firstname;
  private String lastname;
  private String email;
  private Address address;   // nested object, not a foreign key — Mongo embeds it
}

The repository is one line. Extending MongoRepository<Customer, String> gives save, findById, findAll, deleteById for free — Spring Data generates the implementation:

public interface CustomerRepository extends MongoRepository<Customer, String> { }

Request/Response DTOs — Java records

Both DTOs are records, not classes — immutable, no Lombok needed for getters. CustomerRequest carries Bean Validation annotations that run automatically before the controller method body executes:

public record CustomerRequest(
    String id,
    @NotNull(message = "Customer firstname is required") String firstname,
    @NotNull(message = "Customer firstname is required") String lastname,
    @NotNull @Email(message = "...not a valid email address") String email,
    Address address
) {}

Service — the actual logic

Notably: updateCustomer does a partial merge, not a blind overwrite — blank/null fields in the request are left alone (mergeCustomer), and a missing customer throws CustomerNotFoundException, mapped elsewhere to a proper HTTP error by GlobalExceptionHandler.

public void updateCustomer(CustomerRequest request) {
  var customer = repository.findById(request.id())
      .orElseThrow(() -> new CustomerNotFoundException(...));
  mergeCustomer(customer, request);   // only overwrite non-blank fields
  repository.save(customer);
}

Hands-on: run the full CRUD loop

STEP 1

Config server (Lesson 1) and the mongodb container should still be running. Confirm: docker compose ps shows mongo_db up, and curl http://localhost:8888/customer-service/default still responds.

STEP 2

Start the customer service:

cd services/customer
./mvnw spring-boot:run

Watch the log — it reads its Mongo config from the config server, not from its own application.yml, then connects to Mongo on port 27017.

STEP 3

Create a customer:

curl -X POST http://localhost:8090/api/v1/customers \
  -H "Content-Type: application/json" \
  -d '{
    "firstname": "Ada",
    "lastname": "Lovelace",
    "email": "ada@example.com",
    "address": { "street": "Main St", "houseNumber": "1", "zipCode": "00001" }
  }'

Response is the new customer's Mongo id — copy it for the next steps.

STEP 4

Fetch it back, list all, and check existence (swap in your id):

curl http://localhost:8090/api/v1/customers/<id>
curl http://localhost:8090/api/v1/customers
curl http://localhost:8090/api/v1/customers/exists/<id>

✓ Also open http://localhost:8081 (mongo-express) and look at the customer database — your document is really there.

STEP 5

Try triggering the validation you read above — omit the email:

curl -X POST http://localhost:8090/api/v1/customers \
  -H "Content-Type: application/json" \
  -d '{ "firstname": "No", "lastname": "Email" }'

You should get a 400 with a validation message, not a 500 or a silently-saved bad record — that's GlobalExceptionHandler + @Valid doing their job.

Check your recall

Why does this service have both a Customer class and a CustomerResponse record with identical-looking fields?

They represent different concerns — DB shape vs. API contract — and are allowed to diverge. The mapper is the only place that knows both.

What happens to a blank firstname sent in a PUT update request?

Nothing — mergeCustomer only overwrites a field if the incoming value is non-blank, so existing data survives a partial update.
