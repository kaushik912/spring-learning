The Big Picture

Why each infrastructure piece in this repo exists — the problem it solves, in one line each. Link back here from any module lesson instead of re-explaining.

The core idea

Instead of one app, this project is 8 small apps, each owning one job (customers, orders, payments, products, notifications), talking to each other over the network. That split is the whole point of "microservices" — but it creates new problems a single app never had. Every extra piece below exists to solve exactly one of those new problems.

The pieces, mapped to problems

Problem, once split into 8 appsThe fixPlain-English job
Each app needs settings (DB passwords, ports) — editing 8 copies is a pain Config Server One shared settings binder every service reads from on startup
Each app's network address can change (restart, scaled up, moved) Eureka Discovery A phonebook — apps register themselves by name, others look them up by name instead of a hardcoded address
An outside caller shouldn't need to know which of 8 services to hit API Gateway One front door — a single public address that routes internally
One service needs an immediate answer from another ("does this customer exist?") Sync HTTP calls (RestTemplate / OpenFeign) Picking up the phone and calling another service directly, live, waiting for the reply
One service shouldn't have to wait for a slow, non-essential step (sending an email) before finishing its own job Kafka (async messaging) A notice board — a service pins an event and moves on; whoever cares reads it whenever they're ready. Neither side needs to know the other exists
A request crosses several services and something's slow or broken — which one? Zipkin (distributed tracing) A tracking slip stamped at every service a request passed through, with timing

Curriculum order (why this order)

The course builds the departments first, then wires them together, in this order:

  1. Sections 5–8 — build each service standalone (Config, Customer, Order, Payment), no cross-talk yet
  2. Section 9 — teach services to call each other directly (sync HTTP)
  3. Section 10 — give them a phonebook so they don't hardcode each other's addresses (Eureka)
  4. Section 11 — put one front door in front of all of them (Gateway)
  5. Section 13 — swap some direct calls for notice-board-style async messaging (Kafka), so services stop blocking on non-essential work
  6. Section 15 — Notification service actually reads the notice board and sends real emails
  7. Section 16 — add tracing so a request across many services is debuggable
Where we are (this workspace) Lessons 1–3 covered Config Server, Customer service, and Order service — all standalone, nothing wired together yet. Order's code already contains the later wiring (it's the finished repo, all sections merged) but can't run end-to-end until Payment, Product, Eureka, Gateway, and Kafka are all up.
