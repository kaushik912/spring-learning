Microservices Communication via HTTP

Order service needs answers from Customer, Payment, and Product right now, synchronously — this is the "picking up the phone" style of communication from the big picture. This repo shows two different Java ways to do it, side by side, in the same class.

New service introduced here: Product

Not in curriculum.txt explicitly, but required for Order to work — it's the thing Order "purchases" from. Same six-layer shape as Customer/Order/Payment (Entity/Repository/DTOs/Mapper/Service/Controller), Postgres-backed, so we won't re-tour it. One difference worth noting:

Product uses Flyway, not ddl-auto: create product-service.yml sets ddl-auto: validate (schema must already match, never auto-created) plus Flyway migrations under db/migration/ — V1__init_database.sql creates the schema, V2__insert_data.sql seeds 25 real products. This is the production-realistic pattern Order/Payment skip for simplicity (recall Lesson 3's callout on why ddl-auto: create isn't safe for real use) — Product actually shows the fix.

OpenFeign: just an interface

@FeignClient(name = "customer-service", url = "${application.config.customer-url}")
public interface CustomerClient {
  @GetMapping("/{customer-id}")
  Optional<CustomerResponse> findCustomerById(@PathVariable("customer-id") String customerId);
}

No implementation body, anywhere. Spring Cloud OpenFeign generates a proxy at startup that turns a call to customerClient.findCustomerById("abc") into an actual GET request. OrderService (Lesson 3) just calls it like a normal method.

RestTemplate: you write every step

public List<PurchaseResponse> purchaseProducts(List<PurchaseRequest> requestBody) {
  HttpHeaders headers = new HttpHeaders();
  headers.set(CONTENT_TYPE, APPLICATION_JSON_VALUE);
  HttpEntity<List<PurchaseRequest>> requestEntity = new HttpEntity<>(requestBody, headers);
  ParameterizedTypeReference<List<PurchaseResponse>> responseType = new ParameterizedTypeReference<>() {};

  ResponseEntity<List<PurchaseResponse>> responseEntity = restTemplate.exchange(
      productUrl + "/purchase", POST, requestEntity, responseType);

  if (responseEntity.getStatusCode().isError()) {
      throw new BusinessException("...");
  }
  return responseEntity.getBody();
}

Same end result as Feign — an HTTP call, a typed response — but every piece (headers, entity, the generic type for a List<PurchaseResponse> response, error checking) is explicit. The ParameterizedTypeReference dance exists because Java erases generic types at runtime — RestTemplate needs to be told exactly what shape to deserialize into.

order/.../product/ProductClient.java · config/RestTemplateConfig.java

Why this repo shows both instead of picking one It's a deliberate teaching choice (the curriculum literally has "RestTemplate vs OpenFeign" as a heading). In real projects you'd normally standardize on one — Feign is more common today for exactly the reason you can see above: less code, same result, and it composes with Eureka name-based routing (next lesson) automatically.

Check your recall (spot the bug — same game as Lesson 3)

@FeignClient(
    name = "product-service",     // <-- look closely
    url = "${application.config.payment-url}"
)
public interface PaymentClient {
  @PostMapping
  Integer requestOrderPayment(@RequestBody PaymentRequest request);
}
What's wrong with PaymentClient's @FeignClient annotation, and does it actually break anything right now?

The name says "product-service" but this is clearly the payment client (calling payment-url) — looks like a copy-paste from ProductClient/a neighboring class. It doesn't break anything yet because a hardcoded url is supplied, which takes priority — Feign dispatches straight to that URL and ignores name entirely for routing. name only becomes load-bearing once url is removed and Feign has to resolve the target via Eureka by service name instead — which is exactly Section 10, next. If that migration happens without fixing this typo, requests to Payment would suddenly start resolving against wherever "product-service" is registered — a real bug waiting to activate.

Hands-on: exercise Product service standalone

We still can't run Order's full createOrder (needs Eureka + Gateway first — next two lessons). But we can prove Product service itself, and see the RestTemplate-called endpoint work directly.

STEP 1

The product Postgres database is already created. Start the service:

cd services/product
./mvnw spring-boot:run

Runs on port 8050. Watch the log for Flyway: Migrating schema "public" to version "1" then "2" — that's the seed data loading.

STEP 2

List the seeded products:

curl http://localhost:8050/api/v1/products

✓ 25 products across 5 categories. Note product id 1 — "Mechanical Keyboard 1", quantity 10.

STEP 3

Call the exact endpoint ProductClient.purchaseProducts calls, directly — buy 2 of product 1:

curl -X POST http://localhost:8050/api/v1/products/purchase \
  -H "Content-Type: application/json" \
  -d '[{ "productId": 1, "quantity": 2 }]'

Then check the stock actually decremented:

curl http://localhost:8050/api/v1/products/1

✓ availableQuantity should now read 8. This is exactly what happens inside createOrder — just called directly instead of through Order.

STEP 4

Try to over-buy and trigger the business-rule exception on purpose:

curl -i -X POST http://localhost:8050/api/v1/products/purchase \
  -H "Content-Type: application/json" \
  -d '[{ "productId": 1, "quantity": 9999 }]'

Expect a 4xx from ProductPurchaseException ("Insufficient stock quantity...") — and quantity should be unchanged after, since the whole method is @Transactional.
