Distributed Tracing

The tracking-slip piece from the big picture — running since Lesson 1's docker-compose.yml, never actually used until now. This is also the lesson that fulfills this whole workspace's stated goal: watching one request travel across every service, visually.

Zero new code — again

Go back and look at Lesson 1's pom.xml excerpt: every service has had micrometer-tracing-bridge-brave and zipkin-reporter-brave on its classpath since Section 4 (Bootstrap). The only thing missing this whole time was using it, and that turns on via one setting, sitting in a file we haven't looked closely at yet:

management:
  tracing:
    sampling:
      probability: 1.0

config-server/.../configurations/application.yml

New idea: application.yml is the shared-defaults file Every other config file you've read has been named after a specific service (customer-service.yml, order-service.yml...). This one is literally named application.yml — Spring Cloud Config's native mode treats that filename specially: its contents apply to every client, merged underneath each service's own specific file. This is where the shared Eureka URL and this tracing setting live, so every service gets them without repeating the config 8 times.

sampling.probability: 1.0 means "trace 100% of requests" — fine for a demo with a handful of manual test calls, wildly expensive at real production traffic (recording and shipping a trace has real CPU/network cost per request). A real system usually samples a small fraction (e.g. 0.1 = 10%) and relies on always-sample-on-error rules for the rest.

Where do the traces go? Nowhere configured explicitly — Spring Boot defaults management.zipkin.tracing.endpoint to http://localhost:9411/api/v2/spans the moment zipkin-reporter-brave is on the classpath, which happens to be exactly where the zipkin container from docker-compose.yml listens. Another "convention over configuration" default, same pattern as everything else in this course.

Check your recall

Why would a real production system almost never set sampling.probability: 1.0?

Cost, at scale — every traced request adds overhead (span creation, network calls to ship them to a collector) multiplied by real production request volume, which is orders of magnitude higher than a few manual demo curls. Most systems sample a small percentage and lean on "always trace requests that error" rules instead of tracing everything.

What's the practical value of seeing order-service's span nested under gateway's in the same trace, versus just reading each service's logs separately?

Logs are per-service and per-line, with no built-in way to know "these 5 log lines across 4 services all belong to the same customer request." A trace answers exactly that — one identifier (the trace id) ties every hop together with real relative timing, which is what actually lets you find the slow or failing hop in a chain like this one without manually correlating timestamps across terminals.
