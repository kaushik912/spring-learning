Service Discovery with Eureka

The phonebook piece from the big picture table. This one closes a loop you've already seen: the "connection refused to localhost:8761" noise from Lesson 2.

The whole server, again, is one annotation

@EnableEurekaServer
@SpringBootApplication
public class DiscoveryApplication {
  public static void main(String[] args) {
    SpringApplication.run(DiscoveryApplication.class, args);
  }
}

discovery/.../DiscoveryApplication.java

Its own config sets two flags that only make sense once you know what they normally do:

eureka:
  instance:
    hostname: localhost
  client:
    registerWithEureka: false   # don't register myself as an entry in the phonebook
    fetchRegistry: false        # don't ask another Eureka server for a copy of the phonebook
  server:
    port: 8761

config-server/.../configurations/discovery-service.yml

Why turn those off? A production Eureka setup often runs multiple Eureka servers that are peers of each other — each one is simultaneously the phonebook and a client registering with the others, for redundancy. This repo runs exactly one Eureka server, so it has nothing to register with or fetch from — hence both flags are off.

Nothing to change in Customer, Order, Payment, or Product

This is the payoff for the noise you saw back in Lesson 2. Every service already had spring-cloud-starter-netflix-eureka-client on its classpath since Section 4 (Bootstrap), and Spring Cloud auto-registers as a Eureka client purely from that dependency being present — no annotation, no code. They've been retrying a registration call to localhost:8761 this whole time and failing. The moment a real Eureka server exists at that address, they'll succeed automatically, with zero code changes.

Hands-on: watch registration happen live

STEP 1 
cd services/discovery
./mvnw spring-boot:run

Runs on port 8761.

STEP 2

Open http://localhost:8761 in a browser — the Eureka dashboard. Under "Instances currently registered with Eureka", it's empty (or close to it) at first.

STEP 3

Make sure customer-service, order-service, payment-service, and product-service are all still running from earlier lessons (restart any you'd stopped: cd services/<name> && ./mvnw spring-boot:run).

STEP 4

✓ Refresh the dashboard within ~30 seconds (Eureka's default heartbeat interval) — you should see CUSTOMER-SERVICE, ORDER-SERVICE, PAYMENT-SERVICE, PRODUCT-SERVICE appear, each showing the host/port they registered with. Note the names are upper-cased automatically from each service's spring.application.name.

You may see an "EMERGENCY! renewals are lesser than threshold" banner That's Eureka's self-preservation mode — it expects a certain rate of renewal heartbeats and gets suspicious when too few instances are registered (common with only 3-4 services in a dev setup). It's a defensive warning, not a failure — safe to ignore here.

Check your recall

Why didn't Customer/Order/Payment/Product need any code or dependency changes to start appearing in Eureka?

They were already Eureka clients since Section 4 — the starter dependency alone triggers auto-registration against Eureka's default address (localhost:8761). They'd been failing silently (or noisily, in the logs) the whole time simply because nothing was listening there yet.

Recall the PaymentClient bug from Lesson 5 (name = "product-service" but calling payment-url). Now that Eureka is running, is that bug still harmless?

Still harmless for now — PaymentClient still has a hardcoded url attribute, which Feign uses directly and ignores name entirely for routing. The bug only becomes live/dangerous the moment someone removes url so Feign has to resolve the target by looking up "product-service" in the registry you're looking at right now — at which point payment calls would silently route to wherever PRODUCT-SERVICE is registered instead.
