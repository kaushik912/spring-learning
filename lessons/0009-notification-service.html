The Notification Service

The other half of Lesson 8's "notice board." Order and Payment have been pinning notes to order-topic/payment-topic since Lesson 4 — this is the service that finally reads them and sends real email.

The consumer: one class, two listeners

@KafkaListener(topics = "payment-topic")
public void consumePaymentSuccessNotifications(PaymentConfirmation paymentConfirmation) {
  repository.save(Notification.builder()
      .type(PAYMENT_CONFIRMATION)
      .notificationDate(LocalDateTime.now())
      .paymentConfirmation(paymentConfirmation)
      .build());
  emailService.sendPaymentSuccessEmail(...);
}

@KafkaListener(topics = "order-topic")
public void consumeOrderConfirmationNotifications(OrderConfirmation orderConfirmation) {
  repository.save(Notification.builder()
      .type(ORDER_CONFIRMATION)
      .notificationDate(LocalDateTime.now())
      .orderConfirmation(orderConfirmation)
      .build());
  emailService.sendOrderConfirmationEmail(...);
}

notification/.../kafka/NotificationsConsumer.java

@KafkaListener is the mirror image of @KafkaTemplate.send() from Lesson 8 — Spring subscribes this method to the named topic and invokes it for every message. Each message does two things: gets archived as a Notification document in MongoDB (an audit trail — same @Document pattern as Customer, Lesson 2), then triggers a real email via EmailService.

Notice: the consumer group id looks like two groups, but it's one notification-service.yml sets group-id: paymentGroup,orderGroup. That reads like "subscribe to two groups," but Spring's group-id property takes a single string — the actual consumer group Kafka sees is the literal string "paymentGroup,orderGroup", comma included. Harmless here (both listeners sharing one group name in the same app is fine — a consumer group is just an offset-tracking bucket, and each listener tracks its own topic's offsets within it), but almost certainly not what whoever wrote it intended to express.

Sending the email

EmailService uses a real SMTP client (JavaMailSender) pointed at MailDev (the mail-dev container from docker-compose.yml since Lesson 1 — a fake SMTP server that catches everything instead of delivering it), renders an HTML template with Thymeleaf, and sends it. Both methods are @Async — the Kafka listener thread doesn't block waiting for the email to actually send.

Hands-on: watch old and new messages get consumed

Notification's config sets auto-offset-reset: earliest, and its consumer group has never consumed before. That combination means something specific worth predicting first.

Predict before you start it You've already put messages on order-topic and payment-topic in Lesson 8, before Notification service ever existed. Given auto-offset-reset: earliest and a brand-new consumer group, what happens to those old messages the moment Notification starts up — are they gone, or does it process them retroactively?

Check your recall

Why did messages from Lesson 8 — sent before Notification service even existed — still get processed?

Kafka doesn't delete messages when they're produced; they sit on the topic until they age out (by retention policy) regardless of whether anyone's consuming. A consumer only "misses" messages that existed before its group first committed an offset if it starts with auto-offset-reset: latest instead of earliest. This consumer group had never consumed before, so earliest meant "start from the very beginning of the topic."

What's the actual, functional consequence of the "paymentGroup,orderGroup" naming mistake?

None, in this exact setup — it's one process with two listeners sharing one (oddly-named) consumer group, which Kafka allows and handles correctly per-topic. It would only become a real problem if someone later split payment and order consumption into two separate services expecting two separate groups, and copied this string verbatim.

Primary source

Spring for Apache Kafka — @KafkaListener reference — and for the offset-reset behavior specifically, Kafka's own auto.offset.reset docs.
